# 低空空管接口自动化测试用例计划

## 一、现状分析

### 1.1 现有测试用例分析（基于 低空空管自动化系统-空域情报接口.json）

根据测试人员编写的 `空域情报_起降场.jmx` 测试脚本，分析现有测试用例覆盖情况：

| 维度 | 分析结果 |
|------|----------|
| **测试模块** | 起降场管理（空域情报模块子集） |
| **覆盖接口** | 5 个核心接口：查询起降场列表、新增起降场、查看起降场详情、切换起降场状态、编辑起降场、删除起降场 |
| **测试用例数** | 约 19 个测试场景 |
| **测试类型** | 正向用例为主，包含部分负向用例（重复编号验证） |
| **测试数据** | 使用 JMeter 随机函数生成动态数据，包含 4 种起降场类型（起降枢纽、起降场、起降点、临时起降点） |
| **断言方式** | JSON Path 断言，验证 status、code、业务字段 |
| **数据清理** | 包含测试数据清理机制（ForeachController 循环删除） |

**现有用例优点：**
- 使用动态数据生成，避免数据冲突
- 包含数据清理机制，保证环境整洁
- 参数化设计，便于维护
- 包含业务流程串联（增→查→改→删）

**现有用例不足：**
- 仅覆盖空域情报模块的 5 个接口（实际该模块有约 15+ 接口）
- 缺少边界值测试（如超长名称、特殊字符、空值等）
- 缺少异常场景（如无效 token、越权访问、并发冲突等）
- 缺少性能测试场景
- 未覆盖扇区管理、航路航线、空域管理等其他空域情报子模块

## 二、全部生成接口测试用例的可行性分析

### 2.1 可行性结论

**技术上可行，但需要分阶段实施。**

### 2.2 工作量估算

基于行业标准估算（每个接口方法平均需要 4-8 个测试用例）：

| 系统 | 接口方法数 | 每接口用例数 | 预估用例总数 | 人工编写人天 | 自动化生成效率 |
|------|------------|--------------|--------------|--------------|----------------|
| 低空空管自动化系统 | 196 | 4-8 | 784-1568 | 80-160 人天 | 可提升 60-80% |
| 低空运维系统 | 46 | 4-8 | 184-368 | 20-40 人天 | 可提升 60-80% |
| **合计** | **242** | - | **968-1936** | **100-200 人天** | - |

### 2.3 风险与挑战

| 风险项 | 风险等级 | 说明 |
|--------|----------|------|
| 接口依赖复杂 | 高 | 业务流程需要接口串联，如：新增→查询→修改→删除 |
| 数据准备困难 | 高 | 部分接口需要前置数据（如飞行任务依赖飞行计划） |
| 业务逻辑复杂 | 中 | Swagger 无法完全描述业务规则（如状态流转、权限校验） |
| 测试数据管理 | 中 | 动态数据生成、数据清理、数据冲突处理 |
| 环境依赖 | 中 | 需要稳定的测试环境，部分接口依赖外部系统 |
| 用例维护成本 | 中 | API 变更后需要同步更新用例 |

## 三、实施步骤

### 阶段一：基础能力建设（1-2 周）

#### 3.1.1 工具/技能选型决策

**方案对比：**

| 维度 | 使用 api-test-case-generator Skill | 使用 Python 脚本 |
|------|-------------------------------------|------------------|
| **上手难度** | 低（已有现成 Skill） | 中（需要开发） |
| **灵活性** | 中（基于模板生成） | 高（完全自定义） |
| **输出格式** | Postman Collection | 可定制（JMX/Postman/YAML） |
| **业务适配** | 通用规则 | 可针对低空业务定制 |
| **维护成本** | 低 | 中 |
| **批量生成** | 支持 | 支持 |
| **与现有 JMX 集成** | 需转换 | 可直接生成 JMX |

**推荐方案：Python 脚本为主，Skill 为辅**

理由：
1. 团队已有 JMeter 测试基础，需要生成 JMX 格式
2. 低空业务有特殊逻辑（如坐标格式、状态流转），需要定制
3. 便于与现有测试框架集成
4. 可复用现有 JMX 的模板和最佳实践

#### 3.1.2 确定点清单

| 序号 | 需要确定的内容 | 建议方案 | 负责人 |
|------|----------------|----------|--------|
| 1 | 测试用例输出格式 | JMX（与现有保持一致） | 测试团队 |
| 2 | 测试环境地址 | dkkgsit-test.testdolphin.com（沿用现有） | 运维团队 |
| 3 | 认证方式 | JWT Token（沿用现有） | 开发团队 |
| 4 | 测试数据生成策略 | 动态随机 + 时间戳（沿用现有模式） | 测试团队 |
| 5 | 用例分级标准 | P0/P1/P2/P3 四级（见 1.3 节） | 测试团队 |
| 6 | 断言标准 | status=200, code=0 + 业务字段验证 | 测试团队 |
| 7 | 数据清理策略 | 测试后自动清理（沿用现有） | 测试团队 |
| 8 | 接口依赖关系 | 需要梳理业务流程图 | 开发+测试 |
| 9 | 前置数据准备 | 使用 @Setup 方法或数据工厂 | 测试团队 |
| 10 | 并发测试策略 | 核心接口单独设计性能场景 | 性能团队 |

### 阶段二：核心接口覆盖（3-4 周）

#### 3.2.1 优先覆盖范围

**P0 优先级接口（约 80-100 个接口方法）：**

1. **飞行任务模块**（任务创建、查询、变更、取消、审批、放飞申请等）
2. **飞行计划模块**（计划创建、查询、修改、删除、审批等）
3. **空域情报模块**（起降场、扇区、航路、空域的 CRUD）
4. **无人机管理模块**（无人机注册、查询、修改、状态变更等）

#### 3.2.2 实施步骤

```
第 1 周：
├── 梳理 P0 接口清单

├── 设计测试数据工厂

第 2-3 周：
├── 分批生成接口用例
├── 人工评审和补充
├── 执行验证并修复
└── 完善断言和测试数据

第 4 周：
├── 集成到 CI/CD

```

### 阶段三：全面覆盖（4-6 周）

覆盖 P1/P2 优先级接口，完善边界值和异常场景。

### 阶段四：持续优化（长期）

- API 变更自动检测
- 用例自动更新
- 覆盖率监控
- 性能基线建立

## 四、技术方案建议

### 4.1 Python 脚本方案设计

```python
# 核心模块设计
api_test_generator/
├── parsers/
│   ├── swagger_parser.py      # Swagger/OpenAPI 解析
│   └── dependency_analyzer.py  # 接口依赖分析
├── generators/
│   ├── test_case_generator.py  # 测试用例生成器
│   ├── data_generator.py       # 测试数据生成器
│   └── jmx_generator.py        # JMX 文件生成器
├── templates/
│   ├── jmx_template.xml        # JMeter 模板
│   └── assertion_templates.py  # 断言模板库
├── validators/
│   └── schema_validator.py     # 响应结构验证
└── utils/
    ├── data_factory.py         # 数据工厂
    └── coordinate_gen.py       # 低空坐标生成（业务定制）
```

### 4.2 用例生成规则

| 用例类型 | 生成规则 | 数量/接口 |
|----------|----------|-----------|
| 正向用例 | 正常参数，验证成功响应 | 1-2 |
| 边界值用例 | 最小/最大值、空值、超长值 | 2-4 |
| 负向用例 | 必填缺失、类型错误、格式错误 | 2-3 |
| 异常用例 | 无效认证、越权、并发冲突 | 1-2 |
| 业务用例 | 状态流转、业务规则验证 | 1-3 |

### 4.3 与现有 Skill 的结合点

- 使用 `api-test-case-generator` Skill 快速生成 Postman Collection 作为参考
- 提取 Skill 中的测试设计模式，应用到 Python 脚本
- 使用 `testcase-generator` Skill 补充功能测试用例设计思路

## 六、总结与建议

### 6.1 关键结论

1. **可行性**：全部生成是可行的，但建议分阶段实施，优先覆盖 P0 核心接口
2. **工具选择**：推荐 Python 脚本方案，更贴合现有 JMeter 测试框架
3. **投入产出**：自动化生成可节省 60-80% 用例编写时间，但需要前期投入建设生成框架

### 6.2 下一步行动

1. **立即执行**：确认 3.1.2 节的"确定点清单"，特别是接口依赖关系和测试环境
2. **本周内**：搭建 Python 生成脚本基础框架，完成 Swagger 解析模块
3. **下周起**：分批生成并验证 P0 接口用例

### 6.3 风险提示

- 自动生成用例需要人工评审和补充业务场景
- 接口依赖复杂的业务流程需要单独设计
- 建议保留 20-30% 的人工编写比例用于复杂场景
