## 2026-08-03 — 文件列表加载性能优化：消除逐文件磁盘 I/O + content_backup 大字段传输

### 问题背景

每次切换到"数据管理"或仿真执行的"场景文件"页面，文件列表加载都需要一定时间的空白等待。经分析，瓶颈在 `api_db_list_files` GET 接口：

1. **逐文件磁盘 I/O（B1，最严重）**：对列表中每个文件都执行 `open + read 64KB + json.loads` 来做格式检测。page_size=20 即 20 次磁盘读 + 1.25MB + 20 次 JSON 解析；scene 页面用 page_size=200 即 200 次。无任何缓存，每次请求重算。
2. **content_backup 大字段传输（B2）**：`SELECT *` 带回 `content_backup` MEDIUMTEXT（单文件可达 16MB），列表查询传输数 MB 无用数据到 JSON 响应。
3. **`_resolve_path` 逐行文件系统检查**：每行 4-5 次 `os.path.exists` 调用，甚至在 GET 请求期间触发 MySQL 备份恢复写入磁盘。

### 修复方案

**核心思路**：格式检测结果在文件上传/导入时计算一次并缓存到数据库，列表查询直接从 DB 读取，完全消除磁盘 I/O。

**修改 1 — 格式缓存到数据库**：
- `sim_json_files` 表新增 `format` VARCHAR(32) 和 `format_label` VARCHAR(64) 列
- 将 `_detect_file_format()` 从 `web/server.py` 移至 `database/json_data_manager.py`
- `save_file()` 上传时自动检测格式并存入 DB（content 已在内存中，零额外开销）
- `import_from_mock()` 导入时同样检测并存储
- 新增 `_fmt_to_compatible_modes()` 从格式字符串推导兼容模式（无需读文件）
- 新增 `backfill_file_formats()` 回填存量文件的格式字段

**修改 2 — 列表查询排除大字段**：
- `mysql_db_manager.query()` 新增 `columns` 参数支持列筛选
- `list_files()` 明确列出元数据列，排除 `content_backup` MEDIUMTEXT

**修改 3 — 列表接口去磁盘 I/O**：
- `api_db_list_files()` 移除逐文件 `open+read+json.loads` + `_resolve_path` 循环
- 改为从 DB 字段读取格式，通过 `_fmt_to_compatible_modes()` 推导兼容模式
- 同时 pop `content_backup` 防止泄露到前端响应

### 操作清单

|------|------|------|------|
| `database/mysql_db_manager.py` | 修改 | ✅ | DDL 新增 `format`/`format_label` 列；`migrate_schema()` 添加列迁移；`query()` 新增 `columns` 参数 |
| `database/db_manager.py` | 修改 | ✅ | SQLite DDL 同步新增 `format`/`format_label` 列 |
| `database/json_data_manager.py` | 修改 | ✅ | 移入 `_detect_file_format()` + `_fmt_to_compatible_modes()`；`save_file()`/`import_from_mock()` 自动检测格式；`list_files()` 排除 `content_backup`；新增 `backfill_file_formats()` |
| `web/server.py` | 修改 | ✅ | `api_db_list_files()` 移除逐文件磁盘 I/O 循环 + pop `content_backup` |

## 2026-08-03 — 修复 simulator_id 超长导致 JSON 文件上传 500 报错（两轮修复）

### 问题背景

数据管理页面通过 `/api/data/db/files` POST 接口上传 JSON 文件时，后端返回 500 错误。经两轮排查发现两个独立问题：

**第一轮 — simulator_id 超出列宽度**：文件中包含 26 个不同的 `uniqueProductIdentificationCode` 时，`_extract_simulator_id()` 生成 230+ 字符的标识字符串，超出旧版迁移创建的 `VARCHAR(128)` 列限制。

**第二轮 — 未捕获异常触发 WSGI 断言**：修复列宽度后上传仍报 `write() before start_response`。根因是 `api_db_save_file` 缺少 `@_safe_json` 装饰器，导致 `save_file` 之外的代码（如 `_get_json_mgr()`、`uploaded.read().decode()`、编码/内存异常等）抛出的异常未被捕获，传播到 Werkzeug WSGI 层触发断言错误。

### 根因分析

1. **自动检测逻辑生成超长字符串**：`save_file()` 在第 466 行调用 `_extract_simulator_id(content[:131072])` 自动提取 UAV 标识，该函数遍历 JSON 数组提取所有不重复的 `uniqueProductIdentificationCode`，最多展示 10 个 ID
2. **每个 ID 约 20 字符**：10 个 ID × 20 字符 + 分隔符 + " 等 N 架" ≈ 230+ 字符
3. **数据库列宽度不足**：旧版迁移脚本 `migrate_schema_v2.py` 将 `simulator_id` 列创建为 `VARCHAR(128)`，230 字符远超 128 限制 → INSERT/UPDATE 失败 → 500 错误
4. **即使 VARCHAR(2048) 也无保护**：当前 `mysql_db_manager.py` 的 DDL 定义为 `VARCHAR(2048)`，但函数无任何截断保护，极端场景（超长 ID + 多 UAV）仍可能超限

### 修复方案

**防御层 — `_extract_simulator_id()` 输出长度限制**（`database/json_data_manager.py`）：
- 最多展示 ID 数从 10 个降到 5 个（`_MAX_IDS = 5`），减少 ~50% 输出长度
- 新增硬截断保护：输出超过 500 字符时截断并追加 `"..."`（`_MAX_SIMULATOR_ID_LEN = 500`）
- 500 字符远小于 VARCHAR(2048) 限制，确保永不超限

**修复层 — `migrate_schema()` 新增列类型自动拓宽**（`database/mysql_db_manager.py`）：
- 新增 `_MODIFY_COLUMNS` 逻辑：检测到 `simulator_id` 仍为 `VARCHAR(128)` 时自动 `ALTER TABLE ... MODIFY COLUMN ... VARCHAR(2048)`
- 调用 `migrate_schema()` 即可修复存量数据库的列类型

**修正层 — 迁移脚本列定义**（`database/migrations/migrate_schema_v2.py`）：
- `simulator_id` 列定义从 `VARCHAR(128)` 改为 `VARCHAR(2048)`
- ALTER TABLE SQL 中同步修正

**兜底层 — 添加 `@_safe_json` 装饰器**（`web/server.py`）：
- `api_db_save_file` 新增 `@_safe_json` 装饰器，捕获整个函数（包括 `_get_json_mgr()`、文件读取/解码等 try 块之前代码）中的所有异常
- 该装饰器专为防止 `write() before start_response` 错误设计，在 Flask 视图层用 print 记录异常并返回 500 JSON，避免异常传播到 Werkzeug WSGI 层

### 操作清单

| 文件 | 操作 | 状态 | 说明 |
|------|------|------|------|
| `database/json_data_manager.py` | 修改 | ✅ | `_extract_simulator_id()` 最多展示 5 个 ID + 硬截断 500 字符 |
| `database/mysql_db_manager.py` | 修改 | ✅ | `migrate_schema()` 新增 `_MODIFY_COLUMNS` 自动拓宽列类型 |
| `database/migrations/migrate_schema_v2.py` | 修改 | ✅ | `simulator_id` 列定义 VARCHAR(128) → VARCHAR(2048) |
| `web/server.py` | 修改 | ✅ | `api_db_save_file` 新增 `@_safe_json` 装饰器防止 WSGI 异常传播 |

### 汇总

## 2026-07-29 — MySQL 文件存储跨部署同步 + 编辑文件名后仿真执行修复

### 问题背景

系统有两个部署环境（本地 Windows DEV 和 Docker 容器 Linux 服务器），共享同一个 MySQL 数据库但文件存储各自独立。出现两个 bug：

1. **跨部署文件不同步**：部署 A 上传 JSON 文件后，部署 B 预览显示 0 行，"全部导出到磁盘"无法恢复文件
2. **编辑文件名后仿真报错**：在数据管理修改文件名/分类后，仿真执行报"文件不存在"且无法发送数据到下游

### 根因分析

**Bug #1**：`save_file()` 将内容写入本地磁盘后即丢弃，MySQL 表只存 `file_path` 和元数据，不存文件内容（v2 迁移有意移除）。`export_to_mock()` 只能在本地磁盘找到文件时才能复制，无法从数据库恢复。

**Bug #2**：编辑大文件（>100KB，截断加载）时前端不发送 `content`，`save_file()` 跳过磁盘写入，只更新了 DB 中 `name` 字段，`file_path` 和物理文件均不变。仿真执行时前端用 `name`（新名）构造路径 → 文件不存在 → 自动导出回退虽然解析到正确路径加入了 `_existing` 列表，但 `SceneEmitter` 仍被传入 `scene_files`（错误路径）。

### 修复方案

**Bug #1 — MySQL content_backup 兜底**：
- `sim_json_files` 表新增 `content_backup MEDIUMTEXT` 列
- `save_file()` 上传时同步写入 content_backup（≤16MB）
- `_resolve_path()` 磁盘文件缺失时自动从 content_backup 恢复到磁盘
- `export_to_mock()` 磁盘不可用时从 content_backup 重建文件

**Bug #2 — 名称一致性**：
- `save_file()` 更新时若 name 改变且 content 为空，用 `shutil.move()` 重命名物理文件
- `update_file()` 改名时同步重命名物理文件 + 更新 `file_path`
- `export_to_mock()` 用精确路径比较替代"是否在 mock_dir 内"的模糊检查
- `web/server.py` SimulationRunner scene 模式使用 `_existing`（解析后正确路径）传参 SceneEmitter
- `api_launch_replay` 通过 `_resolve_path()` 解析实际文件路径

|------|------|------|------|
| `database/mysql_db_manager.py` | 修改 | ✅ | `sim_json_files` DDL 新增 `content_backup` MEDIUMTEXT 列；`_ensure_mysql_tables()` 和 `migrate_schema()` 两处 `_ALTER_COLUMNS` 新增迁移 |

## 2026-07-23 — 项目启动及数据库连接性能优化

### 修改思路

项目启动时存在多处 MySQL 连接阻塞问题：

1. **模块导入阻塞**：`json_data_manager.py` 在 `import` 时触发 `_migrate_file_paths_once()`，尝试连接 MySQL（5s 超时）
2. **地图渲染阻塞**：`run.js` 中 `await loadEnvSelector()` 等待 MySQL 依赖的 `/api/env/list` 返回后才渲染地图
3. **DDL 持锁阻塞**：`_get_client()` 持锁执行 `SHOW TABLES` + `CREATE TABLE`，多请求并发时延迟累积
4. **关闭慢**：`_graceful_shutdown()` 串行停止 orchestrator 和 sim_runner（各 up to 5s）

### 根因分析

| 症状 | 根因 | 阻塞时长 |
|------|------|----------|
| "数据管理"首次加载不显示数据 | `json_data_manager.py` 模块导入时触发 MySQL 连接 | 5s (超时) |
| "仿真执行"地图加载缓慢 | `run.js` 中 `loadEnvSelector()` 阻塞 `initMap()` | 5s (超时) |
| 首次访问数据库页面慢 | `_get_client()` 持锁执行 DDL | 1-3s (可达时) |
| Ctrl+C 关闭慢 | `_graceful_shutdown()` 串行等待 | 累计 5-15s |

### 执行计划

1. **惰性化**：`_migrate_file_paths_once()` 仅由 `_lazy_init()` 在首次 CRUD 时触发
2. **异步解耦**：`loadEnvSelector()` 改为 fire-and-forget，`initMap()` 立即执行
3. **DDL 与 CRUD 解耦**：建表操作移至 `init_tables()` 在预热阶段完成
4. **并行关闭**：orchestrator 和 sim_runner 改为 daemon 线程并行停止

### 技术细节

- 移除重复的 `_migrate_file_paths_once()` 定义（第49-85行）
- 移除 `_tables_verified` 冗余标志
