下面给出一套**不影响现有运行功能、以渐进迁移为主**的系统文件架构优化建议。当前文档中的项目实际上已经呈现出“核心模拟器 + Web 控制台 + 自动化测试 + HA 测试 + 数据工厂 + Docker + 文档”的大型工程形态，但目录上仍偏“脚本集合式”，核心代码、测试工具、历史备份、运行数据和文档混放较多，不利于后续维护和交接。文档中 `utm_simulator` 是核心运行目录，里面同时包含仿真引擎、Web 服务、配置、数据管理、工具脚本、前端资源、测试、mock 数据、离线包和部署脚本；根目录下还并列存在 `atc_api_autotest`、`atc_ha_test`、`test_data_create`、`atc_test_cases`、`atc_data_factory`、`docker`、`docs` 等大量测试与支撑目录。

## 一、总体优化原则

本次优化不建议做“大拆大改”，而应采用**兼容式重构**：

1. **核心代码先模块化，不直接改业务逻辑**
   先移动目录和补充 `__init__.py`、兼容入口、导入适配层，保证原来的 `start_web.ps1`、`deploy.sh`、`deploy_repeat.sh`、`python main.py`、`python cli.py` 等入口仍可运行。
2. **前后端分离但不强制更换技术栈**
   当前前端是原生 HTML/CSS/JS，后端是 Flask Web 服务和 Socket.IO。优化目标不是马上替换 Vue/FastAPI，而是先把 `backend/`、`frontend/`、`scripts/`、`tests/`、`docs/` 清晰分区。
3. **运行时代码、测试代码、数据制造代码、历史代码分离**
   现在 `tools/`、`test_data_create/`、`atc_test_cases/`、`atc_data_factory/`、`atc_api_autotest/`、`atc_ha_test/` 都承担“测试/数据/运维/诊断”职责，应统一归入 `tests/`、`tools/`、`ops/` 或 `archive/`。
4. **保留旧路径兼容层**
   对外部脚本可能依赖的旧文件，如 `utm_simulator/main.py`、`utm_simulator/web_server.py`、`utm_simulator/tools/run_kafka_alive.py`，不要立即删除，而是改成薄入口，内部转调新包路径。

## 二、当前架构的主要问题

### 1. 核心运行目录职责过重

`utm_simulator/` 当前同时放了仿真核心、Web 后端、前端页面、Kafka/Redis 客户端、配置、数据库、AI 集成、工具脚本、测试、mock 数据、离线包、文档和部署脚本。这个目录已经不是单一 Python 包，而是一个“小型项目根目录”。这会导致新人很难判断哪些文件是生产运行必需，哪些只是诊断、开发或历史参考。

### 2. 测试、压测、HA、数据工厂分散

根目录下的 `atc_api_autotest/`、`atc_ha_test/`、`test_data_create/`、`atc_test_cases/`、`atc_data_factory/` 都与测试、压测、数据构造、运维诊断相关，但命名和层级不统一。它们不应和核心应用目录平级混杂，而应归类到统一的 `tests/`、`qa/`、`tools/` 或 `ops/` 下。

### 3. 历史遗留文件没有物理隔离

文档中已经标注了 `[旧]`、`[待归档]`，但从目录结构看，旧版本脚本、备份文件、旧配置、历史自动化项目仍与当前有效代码放在一起。长期看会带来误执行、误修改、误引用的问题。

### 4. 配置和运行数据边界不清

`env.py`、`config.json`、`data.db`、`mock/*.json`、`lines.json`、`_source/*.json`、`flight_task_templates/*.json` 混在应用目录中。建议区分：

- `config/`：配置模板和环境配置；
- `data/fixtures/`：示例数据；
- `data/runtime/`：运行时生成文件；
- `data/reference/`：参考规范和权威数据；
- `data/mock/`：mock 场景数据。

### 5. 已有优化方案中也指出了重复编排、配置硬编码、日志不规范、测试基础不足等工程化问题，例如 `DataSource/DataFlow` 在多个入口中重复实现、配置密码硬编码在 `env.py`、大量 `print()` 不利于结构化分析等。

## 四、核心目录调整建议

### 1. 将 `utm_simulator/` 拆成标准后端、前端、数据、脚本结构

当前 `utm_simulator/` 是最关键目录，不建议直接大规模删除。推荐先在其内部做分层：

| ---------------------------------------------- | ------------------------------------------------------ | ---------------------- |

## 七、最终建议结论

建议采用“**一主应用、多支撑域、历史归档隔离**”的结构：

```text
apps/utm_simulator/     # 真正的系统主体
qa/                     # 自动化、HA、压测、数据工厂
datasets/               # 场景样本与测试数据
deploy/                 # Docker、Shell、Windows 启动脚本
docs/                   # 架构、接口、部署、使用手册
archive/                # 旧代码、备份、废弃配置
```

这套结构的优点是：

- 核心系统边界更清楚；
- 前后端职责更标准；
- 测试、压测、HA、数据工厂不再污染核心目录；
- 历史代码可追溯但不会误用；
- 后续接入 API、CLI、自动化测试、Docker 发布更自然；
- 保留旧入口后，不会影响现有运行、部署和演示。

最推荐的执行方式是：**先归档外围目录，再包化核心代码，最后再优化导入路径和启动脚本**。不要一开始就修改业务逻辑，也不要一次性删除旧文件。
