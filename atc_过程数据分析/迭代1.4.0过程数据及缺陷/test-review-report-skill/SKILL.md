# 迭代缺陷分析与测试总结报告生成

## 触发条件

当用户执行以下操作时自动调用：
- 上传缺陷清单 Excel 文件（.xlsx/.xls）
- 请求"分析迭代 Bug"、"生成测试总结报告"、"缺陷复盘"
- 提及"迭代缺陷分析"、"集成测试总结"、"缺陷统计"
- 要求"更新报告"、"完善报告"、"生成 Vx.x 版本"

## 执行流程

```
Step 1: 读取 Excel → Step 2: 多维度分析 → Step 3: TOP5 重点剖析
→ Step 4: 过程反思 → Step 5: 改进措施 → Step 6: 生成 Word 报告
```

### Step 1: 数据读取与校验

1. 使用 `pandas.read_excel()` 读取缺陷清单
2. 校验必要字段：`ID`、`标题`、`状态`、`严重程度`、`优先级`、`模块`、`创建时间`、`创建人`、`问题责任人`、`缺陷原因分类`、`问题大类`
3. 如果缺失关键字段，向用户确认字段映射关系
4. 数据清洗：处理 NaN 值、统一时间格式

### Step 2: 多维度统计分析

执行以下分析（代码模板参见 reference.md）：

| 分析维度 | 输出形式 | 关键指标 |
|----------|----------|----------|
| 严重程度分布 | 表格 | 致命/严重/一般/提示/建议 数量及占比 |
| 状态分布 | 表格 | 已关闭/已解决/新/接受处理/挂起/转需求/延期 |
| 优先级分布 | 表格 | 紧急/高/中/低 数量及占比 |
| 模块分布（含严重交叉） | 表格 | 各模块总数+致命+严重+一般+占比 |
| 问题大类分布 | 表格 | 功能问题/界面问题/需求问题/性能问题等 |
| 缺陷根因分类 TOP10 | 表格 | 功能实现逻辑错误/其他/其他/需求问题等 |
| 缺陷创建趋势 | 表格 | 按天统计新增数+累计数 |
| 测试环境分布 | 表格 | 集成测试/客户UAT/test/prod 等环境 |
| 创建人与责任人分布 | 表格 | TOP3 创建人 + TOP5 责任人 |
| 重新打开缺陷 | 明细表 | 严格判断：重新打开时间 > 创建时间 |
| 未关闭缺陷清单 | 明细表 | ID/状态/严重程度/模块/标题摘要 |
| 迭代归属分析 | 表格 | 各迭代缺陷数量及占比 |

**关键判断规则：**
- 重新打开缺陷：严格判断 `重新打开时间 > 创建时间`
- 严重级别以上：致命 + 严重
- 缺陷关闭率：(已关闭 + 已解决) / 总数
- 模块风险等级：缺陷总数 > 30 或 严重缺陷 > 5 为高风险

### Step 3: 重点问题剖析（TOP 5）

根据模块缺陷密度和严重缺陷数量，自动识别 TOP 5 重点模块。每个模块包含：

1. **模块名称与缺陷概况**：总数 + 严重缺陷数 + 占比
2. **典型问题清单**（3-5 条）：从缺陷标题中提取共性模式，例如：
   - 接收机管理：批量导入/配置下发/注册升级/详情查看
   - 态势监视：大数据量/WS 断连/Kafka 超时/航迹展示
   - 告警管理：状态机/抑制逻辑/频繁震荡/配置不生效
   - 任务计划：状态流转/审批逻辑/字段处理/权限控制
3. **根因分析**：基于缺陷原因分类和缺陷定位说明归纳

### Step 4: 过程问题反思

基于数据分析结果，自动生成 5 个维度的深度反思：

1. **需求管理薄弱**：需求问题类缺陷占比，典型场景（最小探测线、ADS-B 数据、边界交互缺失）
2. **代码质量与逻辑错误**：功能实现逻辑错误占比，典型标记（"cd"代码问题），核心逻辑缺乏 CR
3. **缺陷根因分析不规范**："其他/其他"占比，根因标记为空或未填写的情况
4. **修复验证不充分**：重新打开缺陷数，关闭后 3~7 天内重新打开的模式
5. **性能与大数据场景验证不足**：大数据量/高并发相关缺陷，缺乏容量测试基线

### Step 5: 改进建议

从开发过程、测试过程、需求管理三个维度输出改进建议：

**5.1 开发过程改进**
- 加强代码评审，特别是功能逻辑复杂、边界条件多的模块
- 提升单元测试覆盖率，功能实现逻辑错误类缺陷通过单测可有效降低
- 规范缺陷根因分类，避免大量"其他/其他"影响后续质量分析
- 对严重缺陷高发模块进行专项代码走查和重构评估

**5.2 测试过程改进**
- 加强缺陷提交规范，确保模块、根因、责任人字段完整
- 增加接口自动化测试覆盖，减少回归测试人力投入
- 在集成测试前增加冒烟测试环节，提前拦截严重级别缺陷
- 新功能模块补充专项测试方案，避免挂起缺陷过多

**5.3 需求管理改进**
- 加强需求评审参与度，增加异常场景 & 边界条件评审 checklist
- 建立需求变更影响评估机制，避免变更引入新的缺陷
- 对于复合类型缺陷（需求问题|功能问题），建立需求-开发联调机制

### Step 6: 生成 Word 报告

使用 `python-docx` 生成结构化报告，严格遵循以下章节结构（V2.0 模板标准）：

```
一、测试概述
二、缺陷总体统计
  2.1 迭代归属分析
  2.2 问题类型分析
  2.3 缺陷根因分析
  2.4 缺陷状态分布
  2.5 严重程度分布
  2.6 模块分布（含严重缺陷交叉）
  2.7 缺陷创建趋势分析
  2.8 缺陷创建与责任人分析
  2.9 重新打开缺陷分析
三、重点问题剖析（TOP 5）
  3.1 接收机管理模块质量风险
  3.2 态势监视性能与稳定性
  3.3 告警管理逻辑缺陷
  3.4 飞行计划与任务计划状态流转
  3.5 重新打开缺陷——修复验证环节疏漏
四、过程问题反思
  4.1 需求管理薄弱
  4.2 代码质量与逻辑错误
  4.3 缺陷根因分析不规范
  4.4 修复验证不充分
  4.5 性能与大数据场景验证不足
五、改进建议
  5.1 开发过程改进
  5.2 测试过程改进
  5.3 需求管理改进
六、测试结论
  6.1 缺陷密度与质量评估
  6.2 模块质量评估
  6.3 发布建议
  6.4 下一步核心任务
```

**格式规范：**
- 字体：微软雅黑，正文 10.5pt，一级标题 22pt 加粗居中
- 表格：Light Grid Accent 1 样式，表头加粗居中
- 关键数据用表格呈现，分析结论用段落文字总结
- 未关闭缺陷必须列出明细表
- 重新打开缺陷必须列出明细表（含重新打开时间）

**版本号自增规则：**
- 生成报告前检查目标目录是否已存在同名文件
- 若存在，自动提取当前版本号并递增：`_V1.0` → `_V2.0` → `_V3.0`
- 若文件名无版本号，首次递增为 `_V2.0`
- 实现方式参见 reference.md 中的 `get_next_version_path()` 函数

**章节结构规范：**
- 报告共设六个一级标题：一、测试概述；**二、缺陷总体统计**；三、重点问题剖析；四、过程问题反思；五、改进建议；六、测试结论
- 缺陷总体统计下设 2.1-2.9 共九个子节
- 重点问题剖析下设 3.1-3.5 共五个子节（TOP 5）
- 过程问题反思下设 4.1-4.5 共五个子节
- 改进建议不设子标题，直接分开发/测试/需求三维度

## 实用脚本

Skill 目录 `scripts/` 下提供可直接执行的 Python 脚本：

| 脚本 | 用途 | 输入 | 输出 |
|------|------|------|------|
| `analyze_defects.py` | V1.0 基础分析 | Excel 文件 | 控制台统计输出 |
| `analyze_defects_v2.py` | V2.0 扩展分析 | Excel 文件 | 控制台统计输出（含环境/迭代/重新打开） |
| `generate_defect_report.py` | V1.0 报告生成 | Excel 文件 | Word 报告（基础版） |
| `generate_defect_report_v2.py` | V2.0 报告生成 | Excel 文件 | Word 报告（增强版） |
| `generate_defect_report_v3.py` | V3.0 完整报告 | Excel 文件 | Word 报告（含重点剖析+过程反思+改进措施） |

执行方式：
```bash
python scripts/generate_defect_report_v3.py
```

脚本中需修改的变量：
- `excel_path`：缺陷数据 Excel 文件路径
- `output_path`：输出 Word 报告路径
- `project_name` / `iteration`：项目名称和迭代版本
