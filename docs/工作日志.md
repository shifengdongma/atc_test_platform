## 2026-07-29 — MySQL 文件存储跨部署同步 + 编辑文件名后仿真执行修复

### 问题背景

系统有两个部署环境（本地 Windows DEV 和 Docker 容器 Linux 服务器），共享同一个 MySQL 数据库但文件存储各自独立。出现两个 bug：

1. **跨部署文件不同步**：部署 A 上传 JSON 文件后，部署 B 预览显示 0 行，"全部导出到磁盘"无法恢复文件
2. **编辑文件名后仿真报错**：在数据管理修改文件名/分类后，仿真执行报"文件不存在"且无法发送数据到下游

### 根因分析

**Bug #1**：`save_file()` 将内容写入本地磁盘后即丢弃，MySQL 表只存 `file_path` 和元数据，不存文件内容（v2 迁移有意移除）。`export_to_mock()` 只能在本地磁盘找到文件时才能复制，无法从数据库恢复。

**Bug #2**：编辑大文件（>100KB，截断加载）时前端不发送 `content`，`save_file()` 跳过磁盘写入，只更新了 DB 中 `name` 字段，`file_path` 和物理文件均不变。仿真执行时前端用 `name`（新名）构造路径 → 文件不存在 → 自动导出回退虽然解析到正确路径加入了 `_existing` 列表，但 `SceneEmitter` 仍被传入 `scene_files`（错误路径）。

### 修复方案

**Bug #1 — MySQL content_backup 兜底**：
- `sim_json_files` 表新增 `content_backup MEDIUMTEXT` 列
- `save_file()` 上传时同步写入 content_backup（≤16MB）
- `_resolve_path()` 磁盘文件缺失时自动从 content_backup 恢复到磁盘
- `export_to_mock()` 磁盘不可用时从 content_backup 重建文件

**Bug #2 — 名称一致性**：
- `save_file()` 更新时若 name 改变且 content 为空，用 `shutil.move()` 重命名物理文件
- `update_file()` 改名时同步重命名物理文件 + 更新 `file_path`
- `export_to_mock()` 用精确路径比较替代"是否在 mock_dir 内"的模糊检查
- `web/server.py` SimulationRunner scene 模式使用 `_existing`（解析后正确路径）传参 SceneEmitter
- `api_launch_replay` 通过 `_resolve_path()` 解析实际文件路径

### 操作清单

| 文件 | 操作 | 状态 | 说明 |
|------|------|------|------|
| `database/mysql_db_manager.py` | 修改 | ✅ | `sim_json_files` DDL 新增 `content_backup` MEDIUMTEXT 列；`_ensure_mysql_tables()` 和 `migrate_schema()` 两处 `_ALTER_COLUMNS` 新增迁移 |
| `database/json_data_manager.py` | 修改 | ✅ | `save_file()` 写入 content_backup + 改名时重命名文件；`update_file()` 改名时重命名文件 + 更新 file_path；`_resolve_path()` 新增 MySQL fallback（第 5 层）；`export_to_mock()` 修复名称不匹配 + 新增 DB 恢复回退 |
| `web/server.py` | 修改 | ✅ | SimulationRunner scene 模式 SceneEmitter 使用 `_use_files`（`_existing` 优先）；`api_launch_replay` 使用 `_resolve_path()` 解析路径 |

## 2026-07-24 — 分类下拉替换为自定义暗色主题组件

## 2026-07-23 — 项目启动及数据库连接性能优化

### 修改思路

项目启动时存在多处 MySQL 连接阻塞问题：

1. **模块导入阻塞**：`json_data_manager.py` 在 `import` 时触发 `_migrate_file_paths_once()`，尝试连接 MySQL（5s 超时）
2. **地图渲染阻塞**：`run.js` 中 `await loadEnvSelector()` 等待 MySQL 依赖的 `/api/env/list` 返回后才渲染地图
3. **DDL 持锁阻塞**：`_get_client()` 持锁执行 `SHOW TABLES` + `CREATE TABLE`，多请求并发时延迟累积
4. **关闭慢**：`_graceful_shutdown()` 串行停止 orchestrator 和 sim_runner（各 up to 5s）

### 根因分析

| 症状 | 根因 | 阻塞时长 |
|------|------|----------|
| "数据管理"首次加载不显示数据 | `json_data_manager.py` 模块导入时触发 MySQL 连接 | 5s (超时) |
| "仿真执行"地图加载缓慢 | `run.js` 中 `loadEnvSelector()` 阻塞 `initMap()` | 5s (超时) |
| 首次访问数据库页面慢 | `_get_client()` 持锁执行 DDL | 1-3s (可达时) |
| Ctrl+C 关闭慢 | `_graceful_shutdown()` 串行等待 | 累计 5-15s |

### 执行计划

1. **惰性化**：`_migrate_file_paths_once()` 仅由 `_lazy_init()` 在首次 CRUD 时触发
2. **异步解耦**：`loadEnvSelector()` 改为 fire-and-forget，`initMap()` 立即执行
3. **DDL 与 CRUD 解耦**：建表操作移至 `init_tables()` 在预热阶段完成
4. **并行关闭**：orchestrator 和 sim_runner 改为 daemon 线程并行停止

### 技术细节

- 移除重复的 `_migrate_file_paths_once()` 定义（第49-85行）
- 移除 `_tables_verified` 冗余标志
- 代码变化：+40/-65 行，净减少 25 行
