## 一、simulation_core.py 深度解析

`simulation_core.py` 是整个项目的仿真引擎，约 1210 行，负责无人机物理仿真、飞行计划生成和禁飞区管理。

### 1.1 全局常量与配置

```python
# 仿真中心点（北京附近演示区域）
ORIGIN_LAT = 40.01960735975581
ORIGIN_LON = 116.56410476837016

# 地球平均半径（米）
RE_EARTH = 6371000.0

# 仿真有效半径（约800米）
SIM_RADIUS_M = 800.0

# 飞行性能参数
CLIMB_RATE = 15.0       # 爬升率 (m/s)
CRUISE_SPEED = 30.0     # 巡航速度 (m/s)
MAX_HORIZ_ACCEL = 5.0   # 最大水平加速度 (m/s²)
MAX_VERT_ACCEL = 5.0    # 最大垂直加速度 (m/s²)
```

### 1.2 坐标转换算法

`meters_to_geo(lat, lon, dn, de)` 将局部东北方向位移（米）转换为经纬度增量，采用**等距投影（Equirectangular Projection）**近似：

```text
d_lat = dn / RE_EARTH
d_lon = de / (RE_EARTH × cos(lat))

新纬度 = lat + d_lat × 180/π
新经度 = lon + d_lon × 180/π
```

**原理**：
- 北向位移直接按地球半径转换为纬度增量（每弧度 = RE_EARTH 米）
- 东向位移需除以 `cos(lat)` 修正，因为纬线圈长度随纬度增加而减小
- 在 800m 仿真半径内，该近似精度足够（误差 < 0.01%）

### 1.3 无人机标识符分配机制

系统维护了一个包含 350+ 条预定义标识符的表 `UAV_IDENTIFIERS`，每条包含：

- `uniqueProductIdentificationCode`：20 位唯一产品识别码（如 `DJI1MAV101A2B3C4D5E6`）
- `realNameRegistrationSign`：实名登记标识（如 `UAS01DJI1MAV001`）

**分配策略**：
1. 按 `plan_counter` 顺序从表中取用（第 1 架用第 1 条，第 2 架用第 2 条，...）
2. 超出表长（350+ 条）后，由 `_random_aircraft_uid()` 随机生成 20 位大写字母+数字
3. 随机生成的 UID 会检查与当前活跃 agents 的冲突，极端情况下追加序号保证唯一

表选择由 `env.ids_index` 控制：
- `1`（默认）：使用 `UAV_IDENTIFIERS`（350+ 条）
- `2`：使用 `UAV_IDENTIFIERS2`（当前为空）

### 1.4 DroneAgent —— 单架无人机代理

#### 1.4.1 状态机（6 状态）

```text
                        │                └────────┘ │

                         (Trajectory 模式航点循环)
```

#### 1.4.2 轨迹飞行模式（Trajectory, type=0）

**TAKEOFF（状态 1）—— 斜向起飞**：
- 同时向第一个巡航航点水平飞行 + 爬升
- 水平速度和垂直速度按 3D 距离比例分配：`v_horiz = cruise_speed × h_dist/total_dist`
- 到达目标高度 ±5m 或接近目标点时切换为 CRUISE

**CRUISE（状态 2）—— 制动减速算法**：

```python
# 制动距离：提前 4 倍理论制动距离开始减速
brake_dist = cruise_speed² / (2 × MAX_HORIZ_ACCEL) × 4

if dist < brake_dist:
    target_speed = cruise_speed × max(dist / brake_dist, 0.05)  # 线性降速
else:
    target_speed = cruise_speed  # 全速巡航
```

**设计意图**：避免无人机在航点处急停，模拟真实飞行器的平滑减速过程。`4×` 因子提供足够的减速缓冲，`max(..., 0.05)` 防止速度归零导致永远无法到达。

**速度平滑**（`_lerp_vel`）：
- 每步速度变化量不超过 `max_accel × dt`
- 使用 `math.copysign(step, diff)` 保证方向正确

**LANDING（状态 4）—— 平滑降落**：
- 水平速度逐步减速到 0（通过 `_lerp_vel`）
- 垂直速度平滑过渡到 `-CLIMB_RATE/2`（下降率 = 爬升率的一半）
- 高度 ≤ 0.1m 时切换为 FINISHED

#### 1.4.3 区域盘旋模式（Loiter, type=1）

- 以区域对角中点为中心
- 200m 半径圆形盘旋
- 角速度 = `cruise_speed / radius`
- 到达 `plan.end_time` 时进入 LANDING
- 当前代码中该模式被禁用（`plan_num < 0` 恒为 False）

#### 1.4.4 GPS 噪声模拟

```python
self.pos_noise_std = 1.0  # GPS位置测量噪声标准差（米）
```

当前实现中 `meas_lat/meas_lon/meas_alt` 直接等于真实值（未加噪声），但 `TelemetrySnapshot` 中的 `h_accuracy` 和 `v_accuracy` 会被设置为 `1`（米），供下游卡尔曼滤波器使用。

#### 1.4.5 ADS-B 附加信息生成

`sourceType_for_uid(uid)` 和 `ads_b_addInf_for_uid(uid)` 为 sourceType=2（ADS-B）的无人机生成固定附加信息：

- `cs`：航班号（如 CCA1234），前缀从 10 个国内航司代码中哈希选取
- `sil`：监视完好性水平（1-10）
- `ssr`：应答机代码（4 位数字）

同一 UID 每次生成结果固定（基于 MD5 哈希），保证数据一致性。

### 1.5 Simulator —— 仿真管理器

#### 1.5.1 飞行计划生成算法

`generate_plan()` 有三种生成分支：

| 分支               | 概率 | 描述                                                    |
| ------------------ | ---- | ------------------------------------------------------- |
| 区域盘旋（POLY）    | 0%   | 已禁用，生成随机凸多边形区域                              |
| 多边形轨迹（POLYGON）| 50%  | 4-30 边正多边形轨迹，边长 200-1000m，可选择顺/逆时针     |
| ~~随机航路点~~      | 50%  | 10-30 个随机航路点，间距 90-3000m，航向随机转弯          |

**注意**：当前代码中 `plan_num < 0.5` 分支生成为多边形轨迹（`poly_sides = 4~30`），`else` 分支为随机航路点。实际上两个分支都是 type=0（Trajectory），差异在于路径形状。

**计划参数**：
- 巡航高度：50-200m 随机
- 任务时长：约 5400 秒（1.5 小时）
- UAV 分类：从 MICRO/LIGHT/SMALL/MEDIUM/LARGE 中随机选择
- 保护阈值：纵向 200m、横向 100m、垂直 100m

#### 1.5.2 外部计划导入（add_plans）

`add_plans(params)` 从外部 JSON 数据（格式与 `redis_route.json` 一致）导入飞行计划：

1. 按 `sequence` 排序 `routeList`
2. 构建 Waypoint 数组：首段起点 + 每段终点
3. 创建 `DroneAgent`（巡航速度固定为 5 m/s，便于与预生成数据一致）
4. 若 UID 已存在则替换旧代理

#### 1.5.3 禁飞区生成算法

`generate_nfzs(count)` 生成带时间窗的动态 4D 禁飞区：

- **类型**：`noDrone` / `limited` / `danger` / `segregated` 循环分配
- **几何形状**：随机凸多边形（3-10 个顶点），基础半径 800-6000m
- **生成方式**：均匀分布角度 + 随机扰动 → 排序 → 每个顶点半径 ±25% 随机
- **高度范围**：最低 0m，最高 200-1500m 随机
- **时间窗**：未来 0-60s 开始，持续 1800-3600s（30-60 分钟）

## 三、kafka_proc.py 设计

### 3.1 KafkaProducerClient —— 生产者封装

#### 3.1.1 双集群同步

```python
def __init__(self, bootstrap_servers, bootstrap_servers_mirror=None):
    self.producer = KafkaProducer(bootstrap_servers, ...)
    if bootstrap_servers_mirror:
        self.producer_secondary = KafkaProducer(bootstrap_servers_mirror, ...)
```

当 `env.kafka_url2` 非空时，每条消息同时发送到两个集群，实现数据双写容灾。

#### 3.1.2 批量发送（send_bulk）

```python
def send_bulk(self, objs, topic):
    for item in objs:
        self.producer.send(topic, item, key=uid_bytes)   # 主集群
        if self.producer_secondary:
            self.producer_secondary.send(topic, item, ...)  # 镜像集群
    self.producer.flush(timeout=1.0)    # 主集群 flush
    if self.producer_secondary:
        self.producer_secondary.flush(timeout=1.0)  # 镜像集群 flush
```

**设计要点**：
- 使用 `uniqueProductIdentificationCode` 作为 Kafka 消息 Key，保证同一无人机消息始终进入同一分区（保序）
- Flush timeout 设为 1.0 秒，避免副本集群不可达时仿真主线程永久阻塞
- 生产者关闭时 timeout 设为 5.0 秒，给予充足的清理时间

#### 3.1.3 批量发送带确认（send_batch）

`send_batch()` 提供逐条确认的批量发送（`future.get(timeout=10)`），适合重要消息场景，但主流程不使用此方法。

## 五、关键算法与公式

### 5.1 经纬度 ↔ 米坐标转换

**正向（米 → 经纬度）**：
```
Δlat = dn / RE             (弧度)
Δlon = de / (RE × cos(lat)) (弧度)
新坐标 = 原坐标 + Δ×180/π
```

**反向（经纬度 → 米）**：
```
dn = Δlat × RE
de = Δlon × RE × cos(lat)
```

### 5.2 制动距离计算

```
brake_dist = v² / (2 × a_max) × 4
```

- `v²/(2a)` 是运动学最小制动距离
- `×4` 安全因子：提前 4 倍距离开始线性减速，确保平滑到达
- 目标速度：`v_target = v_cruise × max(dist/brake_dist, 0.05)`
- `0.05` 下限防止速度归零导致永远无法到达

### 5.3 冲突航线旋转生成（lines_to_redis_route.py）

`_rotate_lonlat_around_pivot()` 以航线上前半段的某个顶点为枢轴，将整条航线水平旋转指定角度：

```python
# 局部平面近似
dx = RE × cos(lat_pivot) × Δlon  (弧度→米)
dy = RE × Δlat                    (弧度→米)

# 2D 旋转
dx' = cos(θ)×dx - sin(θ)×dy
dy' = sin(θ)×dx + cos(θ)×dy

# 米→经纬度
new_lon = pivot_lon + dx'/(RE×cos(lat_pivot))
new_lat = pivot_lat + dy'/RE
```

**用途**：生成与基准航线共享枢轴点的冲突航线，用于测试冲突检测算法。

**附加设计参数**：

- **默认冲突角**：`--conflict-angle` 参数默认值 `5.0` 度（代码中 `conflict_angle_deg=5.0`），非固定值，可通过命令行按需调整
- **冲突机身份池**：预设 2 条冲突无人机 UID（`ZKJXVT05F5G6H7J8K990`、`ZKJXVT05F5G6H7J8K991`），分别对应 UAS10ZKJXVT0530 和 UAS097H9FSEC401；冲突航线数超出 2 条时，调用 `_random_product_uid()` 生成 `ZKJXVT05` 前缀 + 12 位随机大写字母数字的新标识
- **序列重编号**：旋转后的 `routeList` 按 0 起始重新编号 `sequence`，高度保持原始值（仅水平位置旋转）

### 5.4 速度平滑插值（_lerp_vel）

```python
def _lerp_vel(cur, tgt, max_rate, dt):
    diff = tgt - cur
    step = max_rate × dt
    if abs(diff) <= step:
        return tgt
    return cur + sign(diff) × step
```

限制每步速度变化不超过 `max_accel × dt`，模拟真实飞行器的加速度约束。

### 5.5 ADS-B 哈希分配

```python
def sourceType_for_uid(uid):
    b = md5(uid).digest()[0]
    return 1 + (b & 1)  # 1 或 2，基于哈希最低位
```

**注意**：当前代码中该函数第一行就 `return 1`，所有无人机都被分配为 sourceType=1（无人机），ADS-B 分支未激活。

### 5.6 航线枢轴点启发式选择算法

`lines_to_redis_route.py` 中的 `_pivot_index_first_half(m)` 为冲突航线生成选取旋转枢轴点：

```python
def _pivot_index_first_half(m):
    upper = (m - 1) // 2          # 前半段上界
    cand = max(1, min(m - 2, m // 3))  # 约 1/3 处
    return min(cand, upper)
```

**设计推导**：

1. `m // 3` — 目标落在路径前 1/3 范围，使冲突航线在基准航线前半段产生交叉
2. `min(m - 2, ...)` — 防止枢轴恰好落在倒数第二个航点（降落前），此时剩余路径太短无法形成有效冲突
3. `max(1, ...)` — 防止枢轴落在起点（起点高度为 0，不适合做旋转中心）
4. `upper = (m - 1) // 2` — 最终上界保证枢轴始终在前半段
5. 当 `m=2`（仅 2 个航点）时，`upper=0`、`cand=0`，回归 `pivot_idx=0`

**设计意图**：冲突检测算法的有效性测试需要冲突航线与基准航线存在一个明确的空间交叉点。将旋转枢轴选在前半段（而非中点或端点），生成的冲突航线在早期就会与基准航线分叉，更早触发冲突告警。

### 6.2 transform.py —— 原始计划/遥测格式转换

**设计定位**：将外部系统的原始数据（`_source/plans.json` + `_source/telemetries.json`）转换为项目标准 mock 格式（`mock/redis_route.json` + `mock/kafka_data.json`），是 `lines_to_redis_route.py` → `create_data.py` 主链路之外的另一条数据准备路径。

#### 6.2.1 提取控制机制

两种互斥的提取模式：

| 模式 | 变量 | 行为 |
|------|------|------|
| 切片模式 | `EXTRACT_START=0`, `EXTRACT_END=5` | 对 plans 字典 items 做 `[start:end]` 切片截取；两者均为 0 时取全部 |
| 精确模式 | `EXTRACT_UAV_IDS=["UAV_00001"]` | 非空时覆盖切片模式，仅提取指定 UAV ID 列表 |

#### 6.2.2 轨迹点 → 航段转换（traj_to_route_list）

核心转换算法：遍历轨迹点列表 `traj[]`，相邻两点构成一个航段：

```text
traj[i] → traj[i+1]   →   routeList segment

traj[i].point.lon     →   segmentStartLon
traj[i].point.lat     →   segmentStartLat
traj[i].point.alt     →   segmentStartHeight
traj[i+1].point.lon   →   segmentEndLon
traj[i+1].point.lat   →   segmentEndLat
traj[i+1].point.alt   →   segmentEndHeight
traj[i].seg_h         →   segmentProtectHeight
traj[i].seg_w         →   segmentWidth
```

至少需要 **2 个轨迹点**才能生成 1 个有效航段；点数不足的计划会被静默跳过。

#### 6.2.3 遥测过滤与数据合成

- **allowed_uav_ids**：若 `_source/telemetries.json` 存在，遍历其中遥测数据提取出现的所有 UAV ID，仅保留在遥测文件中也有对应数据的计划——确保每架生成的航线都有配套遥测数据
- **kafka_data 合成**：按 uid 从 telemetries 取数据，转为标准 22+ 字段格式（含 `timestamp`、`longitude`、`latitude`、`speed`、`trackAngle` 等），合并后按 `timestamp` 全局排序输出到 `mock/kafka_data.json`

**配置注意事项**：`EXTRACT_END` 默认值为 5（仅提取前 5 条计划）、`EXTRACT_UAV_IDS` 默认 `["UAV_00001"]`，均为开发测试用小样本。如需全量提取，应将 `EXTRACT_START` 和 `EXTRACT_END` 均设为 0。

### 6.3 create_data.py —— 仿真批量生成 Mock 数据

**设计定位**：使用 `Simulator` 仿真引擎一次性批量完成全部飞行计划的生成与全程遥测记录，输出预生成 JSON 文件供 `run_kafka_alive.py` 使用。

#### 6.3.1 MAX-speed 仿真原理

与 `main.py` 的实时仿真（1 Hz，按真实时间步进）不同，`create_data.py` 以**最大计算速度**运行：

```python
sim_time = earliest_takeoff
while sim_time < latest_landing:
    simulator.step(1.0, sim_time=sim_time)  # 显式 sim_time，不用 time.time()
    sim_time += 1.0
```

一次运行即完成全部飞行仿真（例如 5400 秒/1.5 小时的飞行，在秒级内完成计算），将每架机每秒的遥测数据全部记录到内存列表。

#### 6.3.2 自定义航线追加

若 `mock/redis_route_custom.json` 存在（由 `lines_to_redis_route.py` 生成），调用 `simulator.add_plans()` 导入为额外的 `DroneAgent`，其巡航速度固定为 5 m/s（与外部计划数据一致）。

#### 6.3.3 输出与配置

| 输出文件 | 内容 |
|---------|------|
| `mock/redis_route.json` | 全部飞行计划（随机生成 + 自定义追加），与 `main.py` 的 `_plan_to_route_data` 格式一致 |
| `mock/kafka_data.json` | 全部遥测记录，按秒排列，每条含 `"active": 1` 字段（预生成注入模式的标记） |

#### 6.4.2 GeoJSON 多边形转换算法

`verts_to_geojson_polygon(verts)` 将 `geo.verts[]` 转换为 GeoJSON Polygon 格式：

1. 遍历 `verts[]`，提取 `{lon, lat}` 坐标对
2. 坐标顺序为 `[lon, lat]`（WGS84 经度在前，符合 GeoJSON RFC 7946）

### 6.5 lines_to_redis_route.py —— 航线组装与冲突生成

（第 5.3 节已详述旋转算法，此处补充数据流和航线组装细节。）

#### 6.5.1 完整航线三段组装

`_route_list_from_flight_line()` 从任务 API 响应中提取航段并组装完整航线：

```text
1. [起始段] departurePoint ──▶ 首个 type==2 航段起点
   · 高度从 0 → 首段起点高度
   · 体现从地面起飞至巡航区域的过渡

2. [巡航段] 全部 type==2 的 lineSegments
   · 仅转换 type==2 航段（含起点和终点坐标/高度）
   · 跳过 type==3 等区域段（不参与线性航线）

3. [降落段] 末个 type==2 航段终点 ──▶ arrivalPoint
   · 高度从末段终点高度 → 0
   · 体现从巡航区域降落的过渡

若无 departurePoint/arrivalPoint，则仅输出原始 type==2 航段。
```

所有段按 `sequence` 从 0 起始顺序编号。

#### 6.5.2 UAV 信息匹配

第 i 条 flightLine 对应 `uavInfos[i]`，优先取 `uavIdentifyCode`，其次 `uavId`，作为 Redis Hash 的 field（即无人机唯一标识码）。若某条 flightLine 无匹配的 UAV 信息，生成 `"ZKJXVT05"` + 12 位随机大写字母数字作为 fallback。

#### 6.5.3 链式调用 create_data

脚本末尾通过 `import create_data; create_data.main(target_drones=args.count)` 自动触发完整仿真，将 `mock/redis_route_custom.json` 中的自定义航线与 Simulator 随机生成的补充计划合并，输出 `mock/redis_route.json` + `mock/kafka_data.json`。`--skip-create-data` 标志可跳过此步骤，仅生成 `redis_route_custom.json`。

### 6.6 run_kafka_alive.py 单机循环机制

不同于 `main.py` 的动态生成，`run_kafka_alive.py` 采用**固定数据循环回放**策略：

1. 每条无人机的遥测按 `_uid_record_indices[uid]` 的下标顺序逐秒发送
2. 当某架机游标到达末尾 → 索引归零 → 通过 `_refresh_single_route_redis(uid)` 重新计算起降时间并更新 Redis → 从头发送
3. 各无人机独立循环，不互相等待

```text
无人机 A: [t0, t1, t2, ..., tn] → 归零 → [t0, t1, ...]
无人机 B: [t0, t1, t2, ..., tm] → 归零 → [t0, t1, ...]
          ↑ 各自独立，A 可能比 B 先完成一轮
```

## 八、run_plan.py —— 飞行计划遥测实时插值模式

`tools/run_plan.py`（441 行）是项目的**第三种运行模式**，与 `main.py`（动态仿真）和 `run_kafka_alive.py`（预生成注入）并列。它不依赖仿真引擎（`simulation_core.py`），不需要预生成 JSON 文件，直接从 Redis 中读取飞行计划的航段几何信息，通过**线性插值**实时计算每条 UAV 在当前时刻的位置、速度、航向并发送到 Kafka。

### 8.1 RoutePlanSim 线性插值算法

这是该工具的核心算法，将「航段列表 + 当前时间」映射为「遥测位置」。

#### 8.1.1 构建阶段（`_build_segments`）

1. 按 `sequence` 升序排列 `routeList`
2. 对每段调用 `_horiz_dist_m(s_lon, s_lat, e_lon, e_lat)` 计算水平距离（等距投影近似）
3. 累加求得航线总水平长度 `_total_h`

**水平距离近似公式**（`_horiz_dist_m`）：

```text
mx = (lon2 - lon1) × cos((lat1 + lat2) / 2) × 111320.0
my = (lat2 - lat1) × 110540.0
dist = √(mx² + my²)
```

使用 111320（赤道每度经线米数）和 110540（经圈每度纬线米数）两个尺度因子，在短距离（几十公里内）精度足够。

#### 8.1.2 采样算法（`sample(t)`）

6 步流程：

```text
Step 1 — 边界处理
  t < takeoff  → 返回首段起点，operatingStatus=1
  t ≥ land     → 返回末段终点，operatingStatus=0

Step 2 — 时间归一化
  u = max(0, min(1, (t - takeoff) / duration))
  其中 duration = max(land - takeoff, 1e-6)

Step 3 — 距离目标
  dist_target = u × _total_h
  进度沿水平路径按比例分配（非均匀时间插值）

Step 4 — 段定位
  遍历各段累加其水平长度，定位 dist_target 所在的段索引 seg_idx

Step 5 — 段内线性内插
  local = (dist_target - acc) / seg_h
  lon = s_lon + local × (e_lon - s_lon)
  lat = s_lat + local × (e_lat - s_lat)
  alt = s_a  + local × (e_a  - s_a)

Step 6 — 速度与航向导出
  seg_time = duration × (seg_h / _total_h)
  speed    = seg_h / seg_time            (地速，m/s)
  v_speed  = (e_a - s_a) / seg_time      (垂直速度，m/s)
  heading  = _bearing_deg(s_lon, s_lat, e_lon, e_lat)
```

**关键设计决策**：进度按**水平距离**而非时间均匀分配。这意味着在航线较长、巡航段占比大的场景下，无人机速度自然较高；航线内部各段因水平长度不同，分配的时间也不同——这近似于以恒定地速飞行的真实行为。

#### 8.1.3 方位角计算（`_bearing_deg`）

```python
d_lon = radians(lon2 - lon1)
x = sin(d_lon) × cos(lat2)
y = cos(lat1) × sin(lat2) - sin(lat1) × cos(lat2) × cos(d_lon)
heading = (degrees(atan2(x, y)) + 360) % 360
```

标准大圆方位角公式，输出 0-360°（北向 0°，顺时针）。

### 8.2 PlanRunner 三线程架构

```text
主线程 (_tick_loop, 1Hz)
  │
  ├── _remove_expired()          移除 planLandTime 已过的计划
  ├── RoutePlanSim.sample(now)   对每架活跃机插值采样
  ├── _telemetry_dict()          构建 22+ 字段 Kafka JSON
  └── send_bulk()                批量发送到 uav_runtime_data

watch 线程 (_watch_redis_loop, daemon)
  │
  ├── Redis keyspace 通知        订阅 __keyspace@0__:BIZ_DATA:UAV_ROUTE
  │   └── 收到写入事件 → merge_from_redis()
  └── 60s 兜底轮询               服务端未开启通知时的保底机制
      └── HGETALL → merge_from_redis()

trace 线程 (_consume_uav_runtime_trace, daemon)
  │
  ├── poll(timeout=500ms)        消费 uav_runtime_trace
  ├── redisKey 回查 Redis         通过 get_value_by_key() 获取预测数据
  ├── _allowed_uids_set() 过滤    仅保留活跃计划的预测条目
  └── 打印结果
```

### 8.3 自动时间平移机制

`_shift_and_write_plan(uid, obj)` 是保证下游 UTM 系统激活追踪的关键步骤：

1. 从 Redis 读取计划后，计算 `duration = planLandTime - planTakeoffTime`
2. 将 `planTakeoffTime` 设为 `time.time()`（当前时刻），`planLandTime` 设为 `now + duration`
3. 将修改后的完整 JSON 写回 Redis `BIZ_DATA:UAV_ROUTE`
4. **目的**：下游 UTM 系统通过监听 Redis 变更来激活对某架无人机的追踪；若不做时间平移，过期计划不会被 UTM 引擎响应，遥测数据将因"未申报"而被忽略

### 8.4 遥测字段生成（`_telemetry_dict`）

与 `mock/kafka_data.json` 和 `main.py` 的 `_telemetry_to_kafka_message` 格式完全一致：

- 22+ 标准字段（`uniqueProductIdentificationCode`、`longitude`、`latitude`、`speed`、`trackAngle`、`geodeticAltitude`、`verticalSpeed`、`operatingStatus` 等）
- `sourceType` 固定为 1（无人机）
- `active` 固定为 1
- `timestamp` 从 `time.time()` 转为毫秒（`int(now × 1000)`）

### 8.5 与 run_kafka_alive.py 的核心差异

| 维度 | run_kafka_alive.py | run_plan.py |
|------|-------------------|-------------|
| 数据来源 | 预录制 JSON（`kafka_data.json`）回放 | Redis 航段几何实时插值 |
| 物理模型 | 无（回放预记录坐标） | 线性插值（匀速、无加速/减速/爬升过渡） |
| 时间戳处理 | 更新预记录数据的时间戳 | 每 tick 实时计算 |
| 航线变更 | 需重新运行 `create_data.py` 生成 JSON | Redis 中更新计划即生效 |
| 适用场景 | 长期稳定注入、精确定点回放 | 快速对接已申报计划、无需预生成数据 |

## 九、诊断与辅助工具

### 9.1 kafka_read_latest.py —— Kafka 实时消息捕获

**设计定位**：独立诊断工具，从 Kafka 指定 topic 的最新位点起消费 10 秒，将捕获的消息导出到 `kafka_latest.json`（项目根目录）。

**技术特点**：
- 直接使用 `kafka.KafkaConsumer`（而非项目封装的 `kafka_proc.KafkaConsumerClient`），为独立诊断场景设计，不依赖项目其他模块
- `auto_offset_reset=latest`，`enable_auto_commit=True`
- 启动后先 poll 4 秒触发分区分配 → `seek_to_end()` 跳过历史积压
- 10ms poll 间隔密集采集，每秒汇总打印拉取条数，接近 10s 截止时自动缩短 poll timeout 避免超时

**输出结构**：`kafka_latest.json` 包含 `kafka_url`、`topic`、`duration_seconds`、`message_count` 和完整 `messages` 数组（每条含 `topic`/`partition`/`offset`/`timestamp`/`value`）。

**配置说明**：Kafka 地址在脚本中硬编码（`10.165.19.213:30011`），独立于 `env.py`，使用时需根据目标环境修改。

### 9.2 redis_read_lastest.py —— Redis 数据搜索与备份

**设计定位**：独立诊断/备份工具，通过 SCAN 遍历 Redis 匹配键，类型感知读取全部数据，导出到 `redis_search.json`（项目根目录）。

**类型感知读取**（`_get_value_by_type`）：

与 `redis_client.py` 的 `get_value_by_key` 逻辑等价，支持全部 5 种 Redis 类型：

```text
key_type   →  读取命令        →  后处理
──────────────────────────────────────────
string     →  GET             →  JSON 解析尝试
hash       →  HGETALL         →  逐字段 JSON 解析
list       →  LRANGE 0 -1     →  逐元素 JSON 解析
set        →  SMEMBERS        →  逐元素 JSON 解析
zset       →  ZRANGE WITHSCORES → {value, score} 格式
none       →  返回 None（跳过）
```

**关键技术决策**：
- 使用 `SCAN`（`count=1000`）而非 `KEYS`，避免阻塞生产 Redis
- `--mock` 参数：无匹配键时写入示例结构到文件，便于脚本验证和格式参考
- 默认匹配模式 `BIZ_DATA:UAV_ROUTE`（可修改为其他模式）

**注意事项**：脚本文件名为 `redis_read_lastest.py`（"lastest" 为拼写错误），且 docstring 声称匹配 `uav_runtime_trace_*` 但实际代码中 `REDIS_KEY_PATTERN` 为 `BIZ_DATA:UAV_ROUTE`——docstring 已过时，以实际代码行为为准。

### 9.3 trajectory_accuracy_json.py —— 生产数据精度评估适配器

**设计定位**：薄适配器模式——将 `trajectory_accuracy.py` 的默认 `mock/` 目录输入/输出路径替换为 `json/` 目录路径，用于评估生产环境下的轨迹预测精度。

**路径映射**：

| 参数 | mock/ 路径（默认） | json/ 路径（本适配器） |
|------|-------------------|----------------------|
| `--simulated` | `mock/kafka_data.json` | `json/kafka_data.json` |
| `--predicted` | `mock/redis_trace.json` | `json/redis_trace.json` |
| `--html` | `mock/trajectory_accuracy_report.html` | `json/trajectory_accuracy_report.html` |

**实现方式**：通过 `subprocess.run` 以子进程方式调用 `trajectory_accuracy.py`，保持父子进程环境隔离。运行前检查脚本路径和数据文件是否存在，缺失时输出友好错误提示。
