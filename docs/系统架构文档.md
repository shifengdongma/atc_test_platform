## 一、项目概述

### 1.1 项目定位

**utm_moc52** 是一个 UTM（Unmanned Aircraft System Traffic Management，无人机交通管理）仿真与数据注入服务。其核心功能是：

- **仿真多架无人机**：通过 Python 仿真引擎模拟多架无人机的飞行过程，包括动力学、航路点跟踪、区域盘旋等
- **飞行计划注入 Redis**：将生成的飞行计划写入 Redis Hash `BIZ_DATA:UAV_ROUTE`，供下游 UTM 系统查询
- **实时遥测注入 Kafka**：将仿真生成的实时遥测数据写入 Kafka Topic `uav_runtime_data`，供下游态势感知、算法模块消费
- **消费轨迹预测反馈**：从 Kafka Topic `uav_runtime_trace` 消费下游系统的轨迹预测结果，形成闭环

### 1.2 技术栈

| 组件       | 技术选型                                      |
| ---------- | --------------------------------------------- |
| 语言       | Python 3.10+                                  |
| 缓存/存储  | Redis（飞行计划、空域数据）                   |
| 消息队列   | Kafka（遥测数据、轨迹预测反馈）               |
| 数据结构   | ctypes（与 C++ UTM 核心库二进制兼容）         |
| 部署       | Shell 脚本 + Dolphin 海豚运维平台             |
| 依赖管理   | pip + 离线 wheel 包（`packages/` 目录）       |

### 1.3 运行环境

- **开发环境**：Windows / Linux，Python 3.10+
- **生产环境**：Linux 服务器（Dolphin 海豚运维平台 K8s 容器），路径 `/opt/kdm/utm_moc`

### 3.2 数据流详解：main.py 动态仿真模式

1. **启动阶段**：
   - `DataFlow.__init__()` 创建 `DataSource`（连接 Redis + Kafka 生产者 + Kafka 消费者）
   - 启动两个守护线程：仿真线程（1 Hz）和 trace 消费线程（0.1s 轮询）

2. **仿真循环**（每秒一次）：
   - `DataSource.get_flight_plans_simulator()` 被调用
   - `Simulator.step(1.0)` 推进所有活跃无人机状态
   - 移除已完成的无人机，补充新无人机到 `TARGET_DRONES` 数量
   - 新飞行计划通过 `add_redis_plan()` 写入 Redis
   - 所有遥测数据通过 `kafka_producer.send_bulk()` 写入 Kafka

3. **Trace 消费循环**（独立线程）：
   - 轮询 Kafka `uav_runtime_trace`
   - 解析消息中的 `redisKey`，从 Redis 读取预测数据
   - 过滤保留活跃无人机的条目，打印到控制台

### 3.3 数据流详解：run_kafka_alive.py 预生成数据注入模式

1. **启动阶段**：
   - 从 `mock/redis_route.json` 读取预生成航线，时间平移到当前，写入 Redis
   - 从 `mock/kafka_data.json` 读取预生成遥测数据，按 UID 建立索引

2. **注入循环**（每秒一次）：
   - 每个 UID 各取一条遥测记录，时间戳改为当前时间
   - 批量发送到 Kafka `uav_runtime_data`
   - 单个 UID 的遥测发完后，立即刷新该机 Redis 航线并重新循环

3. **Trace 消费**：与 main.py 模式相同

### 3.4 数据流详解：run_plan.py Redis 计划插值模式

`run_plan.py` 是一种全新的轻量运行模式：不依赖仿真引擎（`simulation_core.py`），不需要预生成 JSON 文件，直接从 Redis 中读取飞行计划的航段几何信息，通过**线性插值**实时计算遥测数据。

**启动阶段**：
1. `PlanRunner.__init__()` 创建 Redis 客户端、Kafka 生产者（可选双集群）、Kafka 消费者（PID 独立 group_id）
2. 首次 `merge_from_redis()` 调用 `HGETALL BIZ_DATA:UAV_ROUTE`，读取全部已申报飞行计划
3. 对每条 `planLandTime > now` 的未着陆计划，调用 `_shift_and_write_plan()` 将起降时间平移到当前时刻并写回 Redis（**触发下游 UTM 激活追踪**）
4. 为每条计划构建 `RoutePlanSim` 对象（缓存航段几何与水平距离）

**三条并行循环**：

```text
┌────────────────────────────────────────────────────────────────┐
│  Redis BIZ_DATA:UAV_ROUTE                                      │
│  · 下游系统写入新计划 / 时间平移回写                                 │
└──────────────────────┬─────────────────────────────────────────┘
                       │ keyspace 通知 / 60s 轮询
                       ▼
           ┌───────────────────────────┐
           │  watch_redis_loop (daemon)│
           │  · 订阅 keyspace 通知      │
           │  · 60s 兜底 HGETALL 轮询   │
           │  · merge_from_redis()     │
           └───────────────────────────┘

┌──────────────────────────┐     ┌──────────────────────────────┐
│  _tick_loop (主线程, 1Hz) │     │  _consume_uav_runtime_trace  │
│  1. _remove_expired()    │     │  (daemon, 500ms poll)        │
│  2. RoutePlanSim.sample()│     │  1. poll uav_runtime_trace   │
│     · 时间归一化           │     │  2. 按 redisKey 回查 Redis    │
│     · 距离目标定位         │      │  3. 按活跃 UID 过滤           │
│     · 段内线性内插         │      │  4. 打印预测结果               │
│  3. send_bulk() → Kafka  │     └──────────────────────────────┘
└──────────────────────────┘
```

**与 run_kafka_alive.py 的核心差异**：
- `run_kafka_alive.py` 回放**预记录的逐秒遥测点**（时间戳更新，内容不变）
- `run_plan.py` 在每 tick 时刻从航段几何**实时插值计算**当前位置、速度、航向
- 因此 `run_plan.py` 完全不需要 `mock/` 目录下的 JSON 文件，也无需运行 `create_data.py`

## 四、三种运行模式对比

| 维度             | main.py (动态仿真)                        | run_kafka_alive.py (预生成注入)            | run_plan.py (Redis 计划插值)            |
| ---------------- | ----------------------------------------- | ----------------------------------------- |
| **启动方式**     | `python main.py`                          | `python tools/run_kafka_alive.py`          | `python tools/run_plan.py`              |
| **部署脚本**     | `deploy.sh`                               | `deploy_repeat.sh`                        | 无独立部署脚本（直接运行 tools/run_plan.py） |
| **数据来源**     | Simulator 实时动态生成飞行计划和遥测       | 预先生成的 JSON 文件（mock/ 目录）         | Redis `BIZ_DATA:UAV_ROUTE` 中的飞行计划 |
| **Redis 写入**   | 仿真过程中动态写入                         | 启动时一次性写入 + 单机循环刷新            | 仅读取 + 时间平移回写（触发 UTM 追踪）    |
| **Kafka 注入**   | 实时仿真遥测                              | 预生成数据按秒回放                        | 航线几何插值计算，实时发送                |
| **无人机数量**   | `TARGET_DRONES`（默认 10）                | `--count`（默认 60）                      | 由 Redis 中未着陆计划数动态决定           |
| **适用场景**     | 开发调试、需要动态飞行行为                 | 生产部署、长期稳定注入、精确数据回放      | 仅需飞行计划即可运行的轻量注入，适合对接已申报计划的测试 |
| **几何仿真**     | ✅ 真实动力学（加速/减速/爬升/降落）       | ❌ 预记录数据点，无实时物理计算            | ❌ 线性插值（匀速沿航线，无加速/减速过渡） |
| **禁飞区**       | ✅ 动态生成                               | ❌ 不涉及                                  | ❌ 不涉及                                  |
| **数据一致性**   | 每次运行数据不同（随机生成）               | 每次运行数据相同（基于固定 JSON）          | 基于 Redis 当前快照，计划变更实时响应      |

## 九、关键技术决策

### 9.1 为什么用 ctypes 而不是 protobuf？

与 C++ UTM 核心库（`libutm_core.so`）通过 ctypes 实现零拷贝的二进制兼容，避免序列化/反序列化开销。Python 端直接操作 C 结构体内存布局。

### 9.2 为什么有两种运行模式？

- **main.py**：适合开发和算法验证，利用仿真引擎动态生成真实飞行行为
- **run_kafka_alive.py**：适合生产环境长期注入，数据可预测、可复现，不依赖仿真引擎的随机性

### 9.3 Kafka 消费者组 ID 为什么带 PID？

`group_id=f"utm_demo_group_{os.getpid()}"`，确保同一主机上多实例同时运行時各自收到全部消息，而不是在组内瓜分分区。这是一种刻意设计：每个仿真实例都需要独立消费全部 trace 消息。

### 9.4 为什么支持双 Kafka 集群？

`kafka_url2` 用于消息双写：向主集群发送的同时同步写入镜像集群。这在跨数据中心容灾或灰度迁移场景中十分有用。
